= DR-01: Align Spockk IR Transformations with Spock AST Transformations

*Status*: Proposed +
*Date*: 2026-03-08 +
*Author*: pshevche

---

== Context

Spockk is a Kotlin compiler plugin that replicates Spock's BDD testing syntax in Kotlin. It transforms Kotlin specs into executable JUnit Platform tests by producing IR (Intermediate Representation) that Spock's runtime (`spockframework/spock`) can interpret via its standard metadata annotations.

Spock itself performs its transformations as Groovy AST transformations at compile time via `SpockTransform`, orchestrating `SpecParser`, `SpecRewriter`, `SpecAnnotator`, `DeepBlockRewriter`, `ConditionRewriter`, and `WhereBlockRewriter`. Because Spockk reuses Spock's runtime (`spock.lang.Specification`, `org.spockframework.runtime.*`), its IR output must match what Spock's runtime expects.

This document captures the differences found between Spockk's current IR transformations and Spock's AST transformations, and defines an implementation plan to close those gaps.

---

== Research: Spock's AST Transformations

=== Transformation Pipeline

Spock's `SpockTransform` operates in the `SEMANTIC_ANALYSIS` compile phase:

1. *SpecParser* — Parses `ClassNode`s that extend `Specification`, building a typed model (Spec → Feature → Block structure). Recognizes block labels: `given:` / `setup:`, `when:`, `then:`, `expect:`, `cleanup:`, `where:`, `and:`, `filter:`.
2. *SpecRewriter* — Performs structural rewrites: renames feature methods, moves field initializers, wraps cleanup blocks in try-finally, rewrites `when:` blocks for exception conditions, inserts block entry/exit calls, handles `old()` capture.
3. *SpecAnnotator* — Adds metadata annotations: `@SpecMetadata`, `@FeatureMetadata`, `@BlockMetadata`, `@FieldMetadata`, `@DataProviderMetadata`, `@DataProcessorMetadata`.
4. *DeepBlockRewriter* + *ConditionRewriter* — Rewrite implicit boolean conditions in `then:` and `expect:` blocks into `SpockRuntime.verifyCondition()` calls with `ValueRecorder` instrumentation.
5. *WhereBlockRewriter* — Transforms `<<` data pipes and data table syntax into data provider/processor methods.

=== Block Label Recognition

Spock's `BlockParseInfo` enum recognises:

[cols="1,1,2"]
|===
| Label | `BlockKind` | Notes

| `given:`
| `SETUP`
| Canonical setup block

| `setup:`
| `SETUP`
| Alias for `given:`

| `when:`
| `WHEN`
| Action block

| `then:`
| `THEN`
| Assertion block; triggers implicit condition rewriting

| `expect:`
| `EXPECT`
| Combined action+assertion; triggers implicit condition rewriting

| `cleanup:`
| `CLEANUP`
| Cleanup block; wrapped in try-finally

| `where:`
| `WHERE`
| Parameterization block

| `and:`
| _(inherits predecessor)_
| Continuation; inherits `BlockKind` from preceding block

| `filter:`
| _(internal)_
| Filters parameterized test iterations
|===

=== Block Entry/Exit Notifications

For every block that supports listeners (all except `where:` and `filter:`), Spock inserts:

[source,java]
----
SpockRuntime.callBlockEntered(this, blockIndex);
// ... block statements ...
SpockRuntime.callBlockExited(this, blockIndex);
----

The `blockIndex` is the 0-based position of the block in the feature's block list (matching the `@BlockMetadata` array). These calls fire events to registered Spock extensions and update the current block in `SpecificationContext`.

=== Implicit Condition Rewriting

In `then:` and `expect:` blocks, Spock's `ConditionRewriter` transforms every boolean expression (without explicit `assert`) into a verified condition:

[source,groovy]
----
// Source:
then:
result == expected

// Transformed:
SpockRuntime.verifyCondition(
  $spock_errorCollector, $spock_valueRecorder.reset(),
  "result == expected", 1, 1, null,
  $spock_valueRecorder.record(
    $spock_valueRecorder.startRecordingValue(0),
    result == expected
  )
)
----

The `ValueRecorder` captures sub-expression values for rich failure messages. Explicit `assert` statements go through `ConditionRewriter.rewriteExplicitCondition()`.

=== Cleanup Block Transformation

When a `cleanup:` block exists, Spock wraps the rest of the feature body in try-catch-finally:

[source,java]
----
Throwable $spock_feature_throwable = null;
try {
  // setup/when/then/expect statements
} catch (Throwable $spock_tmp_throwable) {
  $spock_feature_throwable = $spock_tmp_throwable;
  throw $spock_tmp_throwable;
} finally {
  try {
    // cleanup statements
  } catch (Throwable $spock_tmp_throwable) {
    if ($spock_feature_throwable != null) {
      $spock_feature_throwable.addSuppressed($spock_tmp_throwable);
    } else {
      throw $spock_tmp_throwable;
    }
  }
}
----

=== Exception Condition Handling

When `thrown()` / `notThrown()` appears in a `then:` block, Spock rewrites the preceding `when:` block:

[source,java]
----
// Inserted at the start of when:
setThrownException(null);

// when statements are wrapped:
try {
  // when statements
} catch (Throwable $spock_ex) {
  setThrownException($spock_ex);
}
----

The `then:` block's `thrown(ExceptionType)` call then reads from `thrownException`.

=== `old()` Value Capture

In `then:` blocks, `old(expr)` is rewritten to capture the expression value _before_ the `when:` block executes:

[source,java]
----
// Inserted before the when: block:
def $spock_old_value0 = <expr>

// In then: block, old(expr) is replaced with:
$spock_old_value0
----

=== Data Provider / Processor (Where Block)

Data tables and data pipes (`<<`) are transformed similarly in both Spock and Spockk (this area is largely aligned). Spock's method naming:

* Provider: `$spock_feature_N_Mprov<index>` — identical to Spockk
* Processor: `$spock_feature_N_Mproc` — identical to Spockk
* Filter: `$spock_feature_N_Mfilter` — not present in Spockk

=== `@Unroll` / Iteration Naming

Spock uses `@Unroll` (default in Spock 2+) to report each parameterized iteration separately. Feature names can use `#paramName` interpolation, which the runtime resolves during iteration. This is handled by the runtime, not the compiler transform.

---

== Gaps: Spockk vs. Spock

The following gaps were identified between Spockk's current IR transformations and Spock's expected behaviour.

=== Gap 1: `given:` maps to `null` BlockKind instead of `BlockKind.SETUP`

*Spock*: `given:` / `setup:` → `BlockKind.SETUP` +
*Spockk*: `given` → `null` (omitted from `@FeatureMetadata.blocks`)

In `FeatureBlockLabel.kt`, `GIVEN` has `blockKind = null`. Blocks with `null` blockKind are filtered out of the `@FeatureMetadata` annotation (see `FeatureRewriter.kt`, line 81: `blocks.filter { it.element.label.blockKind != null }`). This means `given:` blocks are invisible to Spock's runtime and any extension querying block metadata.

=== Gap 2: `setup:` block label is not recognised

*Spock*: `setup:` is a valid block label, equivalent to `given:`. +
*Spockk*: Only `given` is recognised; `setup:` would cause a compilation error or be ignored.

=== Gap 3: Block entry/exit notification calls are not inserted

*Spock*: Every block (except `where:` and `filter:`) is wrapped with `SpockRuntime.callBlockEntered(this, i)` / `callBlockExited(this, i)`. +
*Spockk*: No block lifecycle calls are emitted.

This is the most impactful gap: Spock extensions that listen to block events (e.g., for reporting, timeouts, or custom logic) receive no notifications. `SpecificationContext.getCurrentBlock()` is never set, which can cause `NullPointerException`s in extensions that rely on it.

=== Gap 4: `cleanup:` block is not supported

*Spock*: `cleanup:` triggers try-catch-finally wrapping of the feature body. +
*Spockk*: `cleanup` is not a recognised block label.

Without `cleanup:`, Spockk users cannot guarantee resource teardown if an earlier block throws. They must resort to `try/finally` in the feature body manually.

=== Gap 5: Implicit conditions in `then:` / `expect:` are not rewritten

*Spock*: Boolean expressions without `assert` in `then:` and `expect:` blocks are implicit conditions — they are wrapped in `SpockRuntime.verifyCondition()` with `ValueRecorder` instrumentation. +
*Spockk*: Requires explicit `assert` keywords; boolean expressions without `assert` are executed but failures produce no assertion error. Kotlin power-assert enhances explicit `assert` messages but does not make bare boolean expressions into conditions.

This is a *semantic difference*: writing `result == expected` in a `then:` block currently does nothing in Spockk. Users must write `assert result == expected`, which is a departure from Spock idiom.

=== Gap 6: Exception conditions (`thrown()` / `notThrown()`) are not supported

*Spock*: `thrown(SomeException)` in a `then:` block causes the preceding `when:` block to be wrapped in try-catch, storing the thrown exception for assertion. +
*Spockk*: No `thrown()` / `notThrown()` support.

=== Gap 7: `old()` value capture is not supported

*Spock*: `old(expr)` in `then:` blocks captures `expr` before the `when:` block runs. +
*Spockk*: No `old()` support.

=== Gap 8: `and:` block does not inherit predecessor's `BlockKind`

*Spock*: An `and:` block inherits the `BlockKind` of the preceding block (e.g., `and:` after `then:` becomes `THEN`, after `when:` becomes `WHEN`). This means it appears in block metadata with the right kind and description. +
*Spockk*: `and` has `blockKind = null`, so it is also omitted from `@FeatureMetadata.blocks`.

=== Gap 9: `filter:` block in `where:` is not supported

*Spock*: After a `where:` block, a `filter:` block generates a `$spock_feature_N_Mfilter` method used to conditionally skip iterations. +
*Spockk*: No `filter:` support.

---

== Implementation Plan

The following increments are ordered by impact and interdependency. Each increment is independently committable.

---

=== Increment 1 — Fix `given:` and `and:` BlockKind mapping

*Goal*: `given:` maps to `BlockKind.SETUP`; `and:` inherits its predecessor's `BlockKind`.

*Scope*: `spockk-compiler-plugin`, `spockk-core` (if `BlockKind.SETUP` is not already present), `spockk-specs`.

*Changes*:

1. In `FeatureBlockLabel.kt`, change `GIVEN` to use `"SETUP"` as its `blockKind`:
+
[source,kotlin]
----
GIVEN("given", GIVEN_BLOCK_FQN, "SETUP"),
----
2. In `FeatureBlockLabel.kt`, remove the fixed `null` from `AND` and make it dynamically inherit its predecessor. This requires propagating predecessor label info through `FeatureBlockStatements` or the collector.
3. In `FeatureRewriter.kt`, update the filter predicate to also emit `and` blocks (since they now have a resolved kind).
4. In `ValidatingFeatureBlockCollector.kt` or collector infrastructure, thread predecessor label through `AND` blocks so it can resolve its `blockKind` at collection time.
5. Update snapshot tests: add `given:` block to `@FeatureMetadata.blocks` in all affected transformed snapshots.
6. Add a new smoke test that verifies `given:` appears in block metadata with kind `SETUP`.

*Commit message*: `feat: map given: to BlockKind.SETUP and and: to predecessor block kind`

---

=== Increment 2 — Add `setup:` as an alias for `given:`

*Goal*: `setup:` is recognised as a valid block label, equivalent to `given:` / `BlockKind.SETUP`.

*Scope*: `spockk-core`, `spockk-compiler-plugin`, `spockk-specs`.

*Changes*:

1. In `spockk-core`, add a `setup` block label object (analogous to `given`):
+
[source,kotlin]
----
object setup : FeatureBlockLabel("setup")
----
2. In `IrIdentifiers.kt`, add `SETUP_BLOCK_FQN`.
3. In `FeatureBlockLabel.kt`, add `SETUP("setup", SETUP_BLOCK_FQN, "SETUP")`.
4. Update `ValidatingFeatureBlockCollector` to accept `setup:` in the same positions as `given:`.
5. Add compilation and smoke tests for `setup:` blocks.

*Commit message*: `feat: add setup: block label as alias for given:`

---

=== Increment 3 — Insert block entry/exit notification calls

*Goal*: Each block's statements are wrapped by `SpockRuntime.callBlockEntered(this, index)` / `callBlockExited(this, index)`, enabling Spock extensions to observe block transitions.

*Scope*: `spockk-compiler-plugin`, `spockk-specs`.

*Changes*:

1. In `IrIdentifiers.kt`, add the `SpockRuntime` FQN and `callBlockEntered` / `callBlockExited` callable IDs.
2. In `FeatureRewriter.kt`, update `rewriteFeatureStatements()` to wrap each block's statements between `callBlockEntered` and `callBlockExited` calls, passing the spec instance (`this`) and the 0-based block index from the `@FeatureMetadata.blocks` array. Only blocks with a non-null `blockKind` (i.e., blocks that appear in `@FeatureMetadata.blocks`) get wrapped.
3. Update snapshot tests to include the inserted calls.
4. Add a runtime test that verifies block entry/exit events are fired (using a Spock extension stub).

*Notes*:

* The `blockIndex` passed to these calls must match the index within the `blocks` array in `@FeatureMetadata`, not the raw statement index in the feature body.
* `where:` and `filter:` blocks never get these calls.

*Commit message*: `feat: insert SpockRuntime.callBlockEntered/Exited around each block's statements`

---

=== Increment 4 — Support `cleanup:` block with try-finally wrapping

*Goal*: A `cleanup:` block generates a try-catch-finally around the rest of the feature body, ensuring cleanup always runs and suppressed exceptions are properly chained.

*Scope*: `spockk-core`, `spockk-compiler-plugin`, `spockk-specs`.

*Changes*:

1. In `spockk-core`, add a `cleanup` block label object.
2. In `IrIdentifiers.kt`, add `CLEANUP_BLOCK_FQN` and `BlockKind.CLEANUP` reference.
3. In `FeatureBlockLabel.kt`, add `CLEANUP("cleanup", CLEANUP_BLOCK_FQN, "CLEANUP")`.
4. Update `ValidatingFeatureBlockCollector` to validate `cleanup:` block placement (must appear after `then:` / `expect:` and before `where:`).
5. In `FeatureRewriter.kt`, detect when a feature has a `cleanup:` block. If present, generate the try-catch-finally wrapping:
+
[source,kotlin]
----
var $spock_feature_throwable: Throwable? = null
try {
  // non-cleanup blocks
} catch ($spock_tmp_throwable: Throwable) {
  $spock_feature_throwable = $spock_tmp_throwable
  throw $spock_tmp_throwable
} finally {
  try {
    // cleanup statements
  } catch ($spock_tmp_throwable: Throwable) {
    if ($spock_feature_throwable != null) {
      $spock_feature_throwable!!.addSuppressed($spock_tmp_throwable)
    } else {
      throw $spock_tmp_throwable
    }
  }
}
----
6. Add transformation snapshot tests and smoke tests.

*Commit message*: `feat: support cleanup: block with try-finally wrapping`

---

=== Increment 5 — Rewrite implicit conditions in `then:` and `expect:` blocks

*Goal*: Boolean expressions without `assert` in `then:` and `expect:` blocks are implicitly treated as conditions, matching Spock semantics. A failed bare boolean expression produces an assertion error.

*Design decision*: This increment introduces a fundamental semantic change. Two options exist:

*Option A* — Match Spock exactly: wrap bare boolean expressions in `SpockRuntime.verifyCondition()` with a `ValueRecorder`. This reproduces Spock's rich failure output but requires implementing the full `ValueRecorder` wiring in IR.

*Option B* — Lightweight: insert an `assert` around bare boolean expressions in `then:`/`expect:` blocks, deferring rich output to Kotlin power-assert. Simpler IR transformation, but failure messages are power-assert style rather than Spock-style.

*Recommendation*: Start with Option B (assertion insertion) to close the semantic gap. Defer Option A (full condition rewriting with ValueRecorder) as a separate design record if needed.

*Scope*: `spockk-compiler-plugin`, `spockk-specs`.

*Changes* (Option B):

1. In `FeatureRewriter.kt` (or a new `ImplicitConditionRewriter`), walk statements in `then:` and `expect:` blocks. For each statement that is a bare boolean expression (not already an `assert`/`throw`/assignment/call-with-side-effects), wrap it in an `IrCall` to `assert(expr)`.
2. Ensure that assignment expressions, void calls, `throw`, `return`, and variable declarations are not wrapped.
3. Update snapshot tests.
4. Add smoke tests that verify bare boolean conditions without `assert` in `then:` / `expect:` blocks cause test failures when false.

*Commit message*: `feat: treat bare boolean expressions in then:/expect: as implicit conditions`

---

=== Increment 6 — Support exception conditions (`thrown()` / `notThrown()`)

*Goal*: When a `then:` block contains a `thrown(ExceptionType)` call, the preceding `when:` block is wrapped in try-catch that stores the thrown exception.

*Scope*: `spockk-core` (if `thrown` / `notThrown` / `setThrownException` / `getThrownException` are not already exposed), `spockk-compiler-plugin`, `spockk-specs`.

*Changes*:

1. Check whether `Specification.thrown()`, `Specification.notThrown()`, `Specification.setThrownException()` are available from Spock's runtime jar. If so, no core changes needed.
2. In the collector or `FeatureRewriter`, detect calls to `thrown()` / `notThrown()` in `then:` block statements.
3. When detected, wrap the statements of the preceding `when:` block:
+
[source,kotlin]
----
setThrownException(null)
try {
  // when statements
} catch ($spock_ex: Throwable) {
  setThrownException($spock_ex)
}
----
4. Update snapshot and smoke tests to cover both `thrown()` matching and `notThrown()`.

*Commit message*: `feat: support exception conditions with thrown() and notThrown()`

---

=== Increment 7 — Support `old()` value capture in `then:` blocks

*Goal*: `old(expr)` in `then:` blocks evaluates `expr` _before_ the `when:` block runs.

*Scope*: `spockk-core` (expose `old()` shim if not present), `spockk-compiler-plugin`, `spockk-specs`.

*Changes*:

1. Check whether `Specification.old()` is available from Spock's runtime. Spock's Groovy `old(expr)` is a no-op at runtime (the compiler replaces the call); Spockk needs an equivalent marker.
2. In `spockk-core`, expose an `old` function that serves as a marker:
+
[source,kotlin]
----
fun <T> old(value: T): T = value  // marker; compiler replaces this
----
3. In the collector, scan `then:` blocks for calls to `old(...)`.
4. In `FeatureRewriter`, for each `old(expr)` found: create a synthetic `val $spock_old_N = expr` statement, insert it before the `when:` block statements, and replace the `old(expr)` call in the `then:` block with a reference to `$spock_old_N`.
5. Update snapshot and smoke tests.

*Commit message*: `feat: support old() value capture for pre-when expression snapshots`

---

=== Increment 8 — Support `filter:` block for parameterized test filtering

*Goal*: A `filter:` block after `where:` generates a `$spock_feature_N_Mfilter` method that the runtime calls to skip iterations.

*Scope*: `spockk-core`, `spockk-compiler-plugin`, `spockk-specs`.

*Changes*:

1. In `spockk-core`, add a `filter` block label.
2. In `IrIdentifiers.kt`, add `FILTER_BLOCK_FQN`.
3. In `FeatureBlockLabel.kt`, add `FILTER("filter", FILTER_BLOCK_FQN, null)` (no BlockKind — filter is internal).
4. In `ValidatingFeatureBlockCollector`, validate `filter:` may only appear after `where:`.
5. In `InternalIdentifiers`, add `getDataFilterName()` (returns `$spock_feature_N_Mfilter`).
6. In `WhereBlockRewriter`, generate a `filter` method that contains the `filter:` block statements and returns `Boolean`.
7. Update snapshot and smoke tests.

*Commit message*: `feat: support filter: block for conditional iteration skipping in where:`

== Out of Scope

* *Full Spock ValueRecorder / condition rewriting* (Option A for Increment 5): Rich sub-expression recording matching Spock's exact output is complex and deferred. Kotlin power-assert covers the majority of the use case.
* *Mock interaction wiring in `then:` blocks*: Spock moves mock interactions to the preceding `when:` scope and inserts mock controller calls. This is tracked separately.
* *`@Unroll` iteration naming templates*: The `#paramName` interpolation in feature names is a runtime feature concern handled by Spock's iteration runner. No compiler changes are needed unless Spockk adds its own naming templates.
* *`setupSpec` / `cleanupSpec` lifecycle method handling*: These are `@BeforeAll` / `@AfterAll` equivalents, managed by the runtime. No IR transformation is required.
