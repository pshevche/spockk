== Writing Tests

=== Building blocks

Similarly to Spock, Spockk lets you define _https://en.wikipedia.org/wiki/Specification_by_example[specifications]_ that describe expected _features_ of the _system under specification_.
A specification is represented as a Kotlin class, while features are defined as its methods.

[source,kotlin]
----
import spock.lang.Specification

class MyFirstSpecification : Specification() {
    fun `adding an element to a list`() {
        // define preconditions, actions, and conditions
    }
}
----

Spockk expects features to be structured into so-called _blocks_.
The framework provides built-in elements that help you define such blocks using the https://en.wikipedia.org/wiki/Behavior-driven_development[Behavior-Driven Development] style.
Currently, the framework supports the following types of blocks:

- `setup` / `given`: defines feature setup and preconditions;
- `when`: defines actions applied to the system under specification;
- `then`: declares the expected state of the fixture after applying actions;
- `expect`: defines a standalone condition block;
- `cleanup`: defines cleanup logic that always runs, even if the feature fails;
- `and`: allows combining multiple precondition, action, and condition blocks.

A feature method must have at least one block to be eligible for execution.
A block consists of all statements between two block labels, or between a block label and the end of the feature.

[source,kotlin]
----

import io.github.pshevche.spockk.lang.and
import io.github.pshevche.spockk.lang.given
import io.github.pshevche.spockk.lang.`when`
import io.github.pshevche.spockk.lang.then

import spock.lang.Specification

class MyFirstSpecification : Specification() {
    fun `adding an element to a list`() {
        given
        val myList = mutableListOf<Int>()

        `when`
        myList.add(1)

        and
        myList.add(2)

        then
        assert(myList.size == 2)
    }
}
----

=== Conditions

`then` and `expect` blocks describe expected outcomes as _conditions_: boolean expressions that must hold true.
Spockk supports both explicit and implicit conditions.

An explicit condition uses Kotlin's `assert`:

[source,kotlin]
----
then
assert(myList.size == 2)
----

An implicit condition is a bare boolean expression statement, no `assert` needed:

[source,kotlin]
----
then
myList.size == 2
----

Either way, a failing condition renders a diagram showing the value of every sub-expression, making it obvious why the condition failed:

[source]
----
Condition not satisfied:

myList.size == 2
|       |    |
[1]     1    false
----

=== Grouping Conditions

Sometimes you want to check several conditions against the same object, or collect every failure instead of stopping at the first one.
Spockk provides three helper methods for this, usable as a direct statement inside a `then`/`expect` block, or inside a plain (non-feature) helper method of your specification:

- `verify(target) { ... }` scopes conditions to `target` as the implicit receiver, so you don't have to repeat it on every line.
Like a normal sequence of conditions, it fails fast on the first unsatisfied one.
+
[source,kotlin]
----
then
verify(pc) {
    vendor == "Sunny"
    clockRate >= 2333
}
----

- `verifyAll { ... }` / `verifyAll(target) { ... }` behave like `verify`, but collect every failing condition and report them together instead of stopping at the first one.
+
[source,kotlin]
----
then
verifyAll(pc) {
    vendor == "Sunny"
    clockRate >= 2333
}
----

- `verifyEach(things) { ... }` runs the block once per element of `things`, with the current element as the implicit receiver, collecting failures across every element instead of stopping at the first failing one.
An optional second argument customizes how a failing element is identified in the failure message: `verifyEach(things, { it.name }) { ... }`.
+
[source,kotlin]
----
then
verifyEach(pcs) {
    vendor == "Sunny"
}
----

NOTE: These correspond to Spock's `with`, `verifyAll`, and `verifyEach`. Spockk names the first one `verify` instead of `with`, since `with` would otherwise collide with Kotlin's own standard library function of the same name.

==== Known limitations

- `verifyEach` does not yet support the two-argument closure form Spock offers for accessing the element's index (`{ item, index -> ... }`).
- Calling `verify`/`verifyAll`/`verifyEach` from a top-level Kotlin extension function (as opposed to a member method of your specification) is not specially rewritten: the call still runs, just without the implicit-condition sugar inside its block.

=== Specifications as Documentation

Block labels can include natural-language descriptions, making your specifications more expressive and readable — even for non-engineers.

.Block labels with descriptions
[source,kotlin]
----
given("an empty bank account")
// ...

`when`("the account is credited $10")
// ...

then("the account's balance is $10")
// ...
----
